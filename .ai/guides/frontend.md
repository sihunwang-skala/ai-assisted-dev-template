# Frontend / UX Guide (On demand)

1. 구현 전 사용자 행동, 정보 구조, 핵심 화면, 상태 흐름을 먼저 확인한다.
2. `docs/DESIGN_SYSTEM.md`의 브랜드, 색상 토큰, Typography, Spacing, Component 규칙을 따른다. 미정이면 Design Direction을 1개 제안하고 승인받은 뒤 구현한다.
3. Framework는 기존 것을 유지. 새로운 의존성/컴포넌트 라이브러리는 가치와 Bundle/유지보수 비용을 비교하고 승인받는다.
4. 기존 Component와 UI Contract를 재사용하고 중복 컴포넌트나 과도한 추상화를 만들지 않는다.
5. 주요 상태: initial, loading, empty, error, success, offline/timeout, forbidden; 필요없는 상태는 억지 추가하지 않는다.
6. 모바일과 데스크톱에서 실제 콘텐츠로 확인하고, keyboard/focus, 입력 레이블, 대비, 폼 검증을 챙긴다.
7. AI 스타일의 상투적인 Gradient/Card/UI 장식과 과도한 이모지, 부자연스러운 카피를 피한다. 디자인은 도메인과 사용자 과업에 맞춘다.
8. 결과 검증: 기존 스크린 플로우 유지, 중요 화면 스크린샷/Visual Diff, 접근성과 레이아웃 Smoke Test.
9. 승인된 카피/네비게이션 변경 시 디자인 결정 기록에 Before/After를 남긴다.

10. 백엔드가 아직 없으면 mock API로 먼저 진행하되, 엔드포인트마다 실서버로 전환하는 스위치(환경 변수)를 두어 화면 코드는 바꾸지 않는다. 계약 문서는 명세와 어긋나는 곳만 적고, 가능하면 상태값 경계·정렬·막는 쪽을 세는 검증 스크립트를 두며, 실서버가 생기면 같은 검증을 실서버에 돌려 필드 이름과 상태값을 대조한다. 명세 번호를 대조하지 못한 경로는 "추정"으로 표시한다.
11. 서버의 enum과 화면 문구가 다르면 변환을 API 클라이언트 한 곳에서만 한다(응답은 enum -> 문구, 요청은 문구 -> enum). 화면마다 변환하면 어긋난다. 목록을 페이징하지 않기로 했다면 서버가 잘랐을 때(총 개수 > 받은 개수) 개발 콘솔에 경고하도록 해서, 조용히 일부만 보이는 상태를 막는다.
