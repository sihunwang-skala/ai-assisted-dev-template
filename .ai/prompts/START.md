# Prompt: Start New Project

이 Repository는 재사용 Development Template에서 시작했다.

목표: [프로젝트 문제와 사용자 가치 2~3문장]
기본 개발 모드: Hackathon / Product 중 택 1
선호 Client/Backend/AI Stack(선택): [없으면 아직 미정]
예산/기간/데모 기준: [ ]

지침:
1. `AGENTS.md`와 `docs/PROJECT.md`, `docs/REQUIREMENTS.md`의 현재 상태를 먼저 읽어라. 아직 빈 칸이면 위 목표만으로 `docs/PROJECT.md` 초안을 채워 보여 주되, 근거 없는 항목은 `[미정]`으로 남기고 Status는 내가 승인할 때까지 Draft로 둔다. 질문은 한 번에 최대 3개.
2. 불확실한 기능을 확정된 요구사항처럼 구현하지 말아라.
3. 가장 저렴한 기술 구성, MVP 범위, 사용자 흐름, 1개의 Vertical Slice와 최소 Test를 제안하라.
4. 승인된 결정 없이 기존 Requirements/Baseline/Design System을 덮어쓰지 말아라.
5. 아직 코드 작성 전이라면 간단한 구조와 첫 구현 단위만 제시하라. 내가 구현하라고 하면 진행하라.
6. 최대 6단계, 단문 중심으로 답하고 중복 조사/과도한 질문은 피하라.
7. 사실(파일/명령으로 확인함), 가정, 미정을 구분해 표시하라. 확인하지 못한 명령은 `unverified`로 남겨라.
8. 첫 응답 형식: 제안 스택 / MVP 범위 / Vertical Slice 1개 / 최소 Test / 내 승인이 필요한 항목.

## 명세나 고정 범위가 이미 있을 때만 (해커톤처럼 아이디어만 있으면 건너뛴다)
코드 전에 아래 넷을 먼저 한다. 반나절 안에 끝낼 수 있는 분량으로만 한다.
1. 요구사항에 안 바뀌는 번호를 붙인다(`REQ-001`). 이슈, 브랜치, 커밋, 테스트가 같은 번호를 가리키게 한다.
2. `docs/REQUIREMENTS.md`의 "Open items"에 아직 정해지지 않은 것을 적는다. 정해지기 전에는 구현하지 않고, 정해지면 `docs/DECISIONS.md`에 기록한 뒤 해당 줄을 지운다.
3. 문서끼리 모순(상태 이름, 단위, 규칙)을 한 번 찾아 고친다. 코딩 중에 발견하면 훨씬 비싸다.
4. 전부 만들 수 없다면 처음부터 끝까지 이어지는 "핵심 줄"을 REQ 번호 순서로 하나 정하고, 그것을 먼저 끝까지 연결한다. 화면만 늘어나고 서로 이어지지 않는 상태를 피한다.
